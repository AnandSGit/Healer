Quick Start

Healer is a 32-command plugin for Claude Code that turns your AI assistant into a research-augmented development engine. Every command searches the web and official docs before acting, then verifies its work with real tool output.

Installation

git clone https://github.com/AnandSGit/Healer.git
cd Healer && ./install.sh

The installer symlinks all commands into ~/.claude/commands/ and sets up the recipe configuration.

First Commands

/healer:diagnose                 # Quick health check (read-only)
/healer:report                   # Formal health grade
/healer:flow morning             # Daily health routine
/healer:help                     # Interactive help

Build a Feature

/healer:brainstorm my-feature    # Explore the idea (interactive)
/healer:plan my-feature          # Create task plan
/healer:implement my-feature     # Build it with research
/healer:test my-feature          # Write comprehensive tests
/healer:review                   # Code review
/healer:ship                     # PR + merge + deploy

# Or use the flow shortcut:
/healer:flow feature

Supported Stacks

Healer auto-detects and works with: JavaScript/TypeScript, Python, Go, Rust, Swift/iOS, Kotlin/Android, C#/.NET, Flutter/Dart, Ruby, Java, C/C++, Elixir, and more. Detection is based on manifest files (package.json, Cargo.toml, go.mod, etc.) and runs once per session.

Each command follows the shared Enforcement Protocol: research is mandatory, verification is evidence-based, and fixes are verified immediately.

Tip: append ? or --help to any healer command for instant six-section drill-down help (e.g., /healer:flow feature ?).

Core

/healer CORE

Universal Autonomous Codebase Health & Development Engine. The master command that discovers, understands, assesses, researches, plans, executes, and reports across any stack.

What it does

Runs a full 7-phase autonomous healing cycle: Discover (auto-detect stack), Understand (read docs and code), Assess (run all tests), Research (search the web), Plan (create implementation plan), Execute (fix and build), Victory (report results).

Arguments

/healer                              # Full autonomous heal
/healer [description]                # Focused heal on specific area
/healer --check                      # Assessment only (no changes)
/healer --fix                        # Classic test-fix loop only
/healer --plan                       # Generate plan only
/healer --learn [topic]              # Research mode
/healer --implement [feature/spec]   # Full feature implementation
/healer --upgrade                    # Upgrade dependencies
/healer --ref [url/image/figma]      # Use reference as inspiration

Procedure

  1. DISCOVER -- Auto-detect the full technology stack, platform, and toolchain
  2. UNDERSTAND -- Read docs, schemas, APIs, UI, business logic, test files, git history
  3. ASSESS -- Run all test suites, linters, builds; categorize every failure
  4. RESEARCH -- WebSearch and WebFetch for best practices, fixes, patterns
  5. PLAN -- Create ordered, dependency-aware implementation plan
  6. EXECUTE -- Implement at expert quality with continuous verification (max 10 iterations)
  7. VICTORY -- Present formal report with all metrics from actual runs
HARD-GATE: Do not start Phase 6 (Execute) without completing Phase 4 (Research). If Phase 4 produced zero WebSearch/WebFetch/Context7 tool calls, research is NOT complete.

Examples

/healer                                    # Heal everything
/healer auth system with Google + Apple    # Focus on OAuth
/healer --learn "Core Data migration"      # Research and adapt
/healer --implement user onboarding flow   # Build from scratch
/healer --ref https://example.com/feature  # Reference a live site

Related: flow, diagnose, fix

/healer:flow CORE

Flow orchestrator -- chains multiple healer sub-commands into pipelines with gate controls, built-in presets, custom YAML recipes, and smart next-step suggestions.

What it does

Orchestrates multi-command pipelines with three gate types: auto-continue, interactive pause, and must-pass halt. Manages state tracking, resumption, and smart next-step suggestions. Includes 11 built-in presets and supports custom YAML recipes.

Gate Operators

SymbolNameOn SuccessOn Failure
→AUTOContinue automaticallyLog warning, continue
?→INTERACTIVEAsk user to continueAsk user: continue anyway?
!→MUST-PASSContinue to next stepHALT -- no override
HARD-GATE: Must-pass gates (!→) are absolute. If a step fails at a must-pass gate, the flow HALTS. Do not continue. The user must explicitly fix and restart.

Examples

/healer:flow feature                    # Full feature lifecycle
/healer:flow fix                        # Diagnose > fix > test > push
/healer:flow brainstorm → plan → test  # Inline custom chain
/healer:flow diagnose !→ deploy         # Must-pass gate
/healer:flow pre-release                # Custom recipe from YAML

Ideation & Design

/healer:validate

Demand validation diagnostic -- challenges whether an idea is worth building using YC-style forcing questions, The Mom Test principles, lean startup validation, and anti-sycophancy rules.

What it does

Acts as a YC partner conducting office hours. Features 6 forcing questions (Demand Reality, Status Quo, Desperate Specificity, Narrowest Wedge, Observation, Future-Fit), failure pattern detection, anti-sycophancy rules, and mode-appropriate intensity (Founder, Demo, Community, Builder).

HARD-GATE: This is a diagnostic, not a pep talk. Never encourage without evidence. Never validate without proof of demand.

Examples

/healer:validate AI code review tool
/healer:validate marketplace for handmade goods
/healer:validate internal workflow automation

Related: brainstorm, strategy, research

/healer:brainstorm

Interactive Socratic brainstorming -- explores requirements through structured dialogue FIRST, then researches online for inspiration, competing approaches, and real-world lessons. Persists decisions for cross-session continuity.

Procedure

  1. Mode Detection -- Startup, Builder, Learning, or Hackathon intensity
  2. Demand Validation Gate (Startup only)
  3. Understand Local Context -- codebase, git history, patterns
  4. Socratic Discovery (5 rounds) -- Purpose, Scope, Narrowest Wedge, Trade-offs, Success Criteria
  5. Research Phase -- implementation patterns, competitive landscape, Context7
  6. Propose 2-3 Approaches with effort estimates
  7. Challenge Round (Devil's Advocate)
  8. Synthesize and Save to ~/.healer/brainstorms/
HARD-GATE: Do NOT write any code during brainstorming. Brainstorming produces IDEAS and DECISIONS, not implementations.

Examples

/healer:brainstorm user authentication with OAuth
/healer:brainstorm real-time collaboration feature
/healer:brainstorm mobile payment integration

Technical specifications -- acceptance tests (Given/When/Then), API contracts (OpenAPI/JSON Schema), error catalogs, traceability matrices, and non-functional requirements with numeric targets.

Key Sections

HARD-GATE: A requirement without acceptance criteria is just a wish. Every FR MUST have Given/When/Then. Every API MUST have OpenAPI/JSON Schema.

/healer:plan

Implementation planning -- bite-sized tasks (2-5 min each) with dependency tracking, file mapping, requirement traceability, effort estimation with compression ratios, and native task integration.

Procedure

  1. Understand scope, extract numbered REQ-N requirements
  2. Research -- Context7 for current APIs, WebSearch for patterns
  3. Strategic Review Checkpoint (scope, direction, alignment, constraints)
  4. Design Review Checkpoint (UI: interaction states, responsive, a11y)
  5. File Structure Map (every file to create, modify, test)
  6. Decompose into 2-5 min bite-sized tasks
  7. Effort Estimation (boilerplate ~100x, tests ~50x, features ~30x compression)
  8. Create native Claude Code tasks with dependencies
  9. Save plan document and cross-session memory

/healer:tdd

Test-driven development -- strict Red-Green-Refactor cycle. Write failing test, implement minimum code, refactor while green.

RED -- Write ONE failing test, confirm it fails. GREEN -- MINIMUM code to pass. REFACTOR -- Clean up, tests stay green.

HARD-GATE: In RED, MUST run the test and confirm it fails. In GREEN, write ONLY minimum code. If refactoring breaks tests, REVERT immediately.

Examples

/healer:tdd email validation for signup
/healer:tdd calculateShippingCost()
/healer:tdd shopping cart total with tax

Enforcement Protocol

The shared layer ALL commands follow. This prevents common AI-assisted development failure modes.

Research Protocol

HARD-GATE: No code changes without completing research. MUST use actual tools (WebSearch, WebFetch, Context7) -- not training knowledge. Context7 first for libraries, WebSearch for broader context, WebFetch for deep reading.

Verification Protocol

HARD-GATE: No success claims without fresh evidence. Run the command, read complete output, check exit code, count actual pass/fail. Only then fill in the report.
ClaimRequired Proof
"Tests pass"Output showing 0 failures + exit code 0
"Build succeeds"Build command with exit code 0
"Bug is fixed"Previously failing test passes + full suite green
"Performance improved"Before AND after benchmark numbers

Fix-Verify Cycle

HARD-GATE: Apply fix → run verification → confirm output. If it didn't work, REVERT before trying next approach. If 3 attempts fail, STOP and escalate.

Anti-Rationalization

ThoughtRealityAction
"I already know how to fix this"Training data may be outdatedSearch for the actual error
"Research will slow me down"Wrong fixes cost MORE time30 seconds of research saves 30 minutes
"The tests probably pass""Probably" is not evidenceRun the command, read the output
"I'll verify at the end"Can't isolate which fix broke whatVerify after EACH change
"I can see it works from code"Reading is not runningRun it. Testing catches 90% of bugs

The Iron Law

Evidence before assertions. Always. If you haven't run it, you can't claim it. If you haven't searched, you can't prescribe. If you haven't verified, you can't report.
